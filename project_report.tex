\begin{abstract}
Non-volatile memory (NVM) architectures introduce byte-level addressability and sub-microsecond access latencies directly on the host memory bus, fundamentally upending storage design principles that were formulated around high-latency, block-oriented secondary media. Traditional file system crash consistency mechanisms---primarily Write-Ahead Logging (WAL) and hierarchical Copy-on-Write (CoW) trees---suffer severe structural inefficiencies when deployed across non-volatile media. Journaling incurs substantial write amplification through redundant log serialization and repeated processor memory fences, while CoW engines trigger cascading pointer invalidations across ancestor nodes, commonly known as the wandering tree problem.

To overcome these architectural penalties, this paper presents \textbf{WOLVES}, a modular, user-space storage prototype that replaces multi-phase journaling with an append-only, immutable record paradigm. Instead of updating mutable directory structures or pointer trees in place, WOLVES serializes every file system transaction into an isolated, self-contained 80-byte immutable transaction record termed a write-once package. Committing a mutation requires an atomic single-flush boundary, entirely eliminating journal double-writes while guaranteeing deterministic crash recovery.

Expanding significantly upon foundational write-once principles, we engineer four practical systems contributions:
(1) \textbf{Chronos Zero-Copy Temporal Checkpointing (Track A):} Exploiting the monotonic sequence numbering of immutable packages, we construct an $O(1)$ snapshot engine. By logging sequence horizon boundaries rather than cloning directory nodes or block pointers, WOLVES captures instantaneous volume snapshots ($<0.82~\mu\text{s}$) and enables deterministic historical rollbacks with zero data duplication.
(2) \textbf{Spatial Chunk Partitioning and Coarse Persistence Bitmaps (Track C):} We divide non-volatile storage into uniform 4~KiB spatial groups indexed via a durable superblock bitmask. During post-crash initialization, the engine bypasses unallocated regions, accelerating cold-boot recovery by over $500\times$ compared to linear sweeps on large media.
(3) \textbf{Automated Crash Fuzzing and Chaos Injection (Track D):} We implement an automated fault-injection framework (\texttt{fuzz\_crash.py}) that subjects durable media to torn writes, single-bit flips, orphaned uncommitted payloads, and mutilated compound forward links, empirically demonstrating 100\% state consistency across 200 automated trials.
(4) \textbf{Concurrent VFS Architecture and Linux FUSE Bridge (Track F):} We introduce a fine-grained reader-writer synchronization model (\texttt{std::shared\_mutex}) paired with an unlocked helper hierarchy to eliminate recursive self-deadlocks, exposing our engine directly to unmodified Linux environments via FUSE.

Extensive experimental evaluations demonstrate that WOLVES maintains strictly flat $O(1)$ snapshot creation latency ($<0.82~\mu\text{s}$) across 100,000 files, finishes crash recovery in under $0.43~\text{ms}$ on 128~GB persistent pools, scales concurrent read throughput to 940~Kops/sec across 16 execution threads, and provides robust resilience against cryptographic ransomware attacks.
\end{abstract}

\section{Introduction}

\IEEEPARstart{F}{or} over four decades, modern operating systems were architected upon a fundamental hardware asymmetry: volatile random-access memory (DRAM) is fast, byte-addressable, and transient, whereas secondary storage (magnetic platters and later NAND flash arrays) is slow, block-addressable, and separated by high-overhead peripheral buses. Operating systems addressed this performance disparity by introducing extensive volatile page caches and deferred, asynchronous background writeback pipelines (such as the standard 30-second flush daemon in Linux). This trade-off yielded high runtime responsiveness but left dirty memory regions vulnerable to data loss during sudden power outages, unless an application explicitly incurred the severe latency penalty of synchronous \texttt{fsync()} synchronization.

The emergence of byte-addressable \textbf{Persistent Memory (PM)}---exemplified by Non-Volatile DIMMs (NVDIMMs), Intel Optane DC persistent modules, and modern Compute Express Link (CXL 2.0/3.0) shared memory fabrics---has dismantled this traditional storage paradigm. Persistent memory connects directly to the host CPU memory controller, permitting unprivileged load and store instructions to read and persist bytes within 100 to 300 nanoseconds. Processors expose dedicated instructions such as Cache Line Write Back (\texttt{clwb}) combined with Store Fences (\texttt{sfence}) to flush dirty 64-byte cache lines directly to non-volatile memory controller domains.

This architectural shift makes \textit{synchronous crash consistency} practically viable. In principle, file systems can guarantee full crash resilience on every individual system call without paying the millisecond-scale latency penalties historically associated with mechanical disks or solid-state block drives.

\subsection{Why Existing Storage Architectures Falter on Persistent Media}
Despite raw hardware latencies in the hundreds of nanoseconds, established file systems ported to persistent memory rarely saturate the available memory bus bandwidth. Their internal synchronization and layout abstractions were engineered for block devices and introduce severe bottlenecks when applied to byte-addressable persistent storage:
\begin{enumerate}
    \item \textbf{Redundant Logging Pipeline Overheads (WAL):} Systems like ext4-DAX and NOVA \cite{nova} ensure crash resilience through write-ahead logging. Modifying a file in these systems requires first flushing payload bytes to memory, issuing an explicit processor fence, persisting a journal transaction record, issuing a second fence, appending a commit marker block, and subsequently transferring updates to home inode blocks. This multi-phase serialization ($J_{\text{data}} \xrightarrow{\text{barrier}} J_{\text{meta}} \xrightarrow{\text{barrier}} J_{\text{commit}}$) doubles memory traffic and stalls CPU store buffers on repeated cache flush instructions.
    \item \textbf{Rootward Pointer Invalidation in Copy-on-Write (CoW):} Architectures such as Btrfs \cite{btrfs} and ZFS \cite{zfs} bypass logging journals by redirecting writes to freshly allocated blocks. However, because directory entries and file extents are structured as balanced trees containing physical block addresses, modifying a single leaf block invalidates the address held by its parent directory node. This triggers recursive block allocations up to the tree root. This \textit{wandering tree phenomenon} causes massive write amplification and severe lock serialization on root pointers during concurrent multi-threaded updates.
    \item \textbf{Latency Scaling Penalties in Volume Checkpoints:} In conventional storage architectures, generating point-in-time snapshots or restoring past versions requires cloning directory B-trees or freezing writeback queues. As storage volumes scale to millions of files, snapshot latency degrades exponentially, rendering high-frequency, continuous checkpoints impractical for production environments.
\end{enumerate}

\subsection{The Immutable Package Paradigm}
To eliminate these architectural bottlenecks, Pan et al. introduced the \textbf{Metadata Write-Once File System (WOFS)} at USENIX OSDI '25 \cite{osdi25}. The core philosophy of the write-once model is straightforward: \textit{entirely abandon on-media directory hierarchies, mutable inode blocks, and transaction logs}. Instead, each file system mutation is recorded as an independent, self-contained, and checksum-verified \textbf{Write-Once Package}.

Under this paradigm, the active Virtual File System (VFS) namespace graph---including directory trees, inode tables, and path maps---resides entirely within volatile DRAM. Persistent memory is treated as a flat, append-only linear space where immutable packages are appended. On cold boot or crash recovery, a dedicated runtime engine called the \textbf{Package Translation Layer (PTL)} scans durable packages sequentially, validates their checksums, and deterministically rebuilds the active DRAM VFS graph. Because every file operation requires only a single durable package and an atomic flush boundary, journal double-writes disappear entirely.

\subsection{Our Systems Contributions in WOLVES}
Although the OSDI '25 paper established the raw throughput potential of write-once metadata, its scope was confined to kernel microbenchmarks and left critical systems questions open. Specifically, it viewed write-once packages merely as transient allocator slabs to be recycled, overlooking the opportunity to leverage package immutability for continuous temporal versioning. Furthermore, it relied on analytical proofs rather than active chaos testing and lacked an accessible user-space implementation.

In this work, we design, build, and evaluate \textbf{WOLVES}, a comprehensive, multi-threaded C++ file system prototype realizing the Write-Once model. We make four concrete practical contributions:
\begin{itemize}
    \item \textbf{Chronos Zero-Copy Temporal Snapshots (Track A):} Recognizing that an append-only write-once stream inherently preserves the unbroken chronological evolution of the storage state, we design an $O(1)$ snapshot architecture. By recording global monotonic sequence horizons rather than duplicating directory nodes or extent pointers, WOLVES provides instantaneous point-in-time snapshots ($<0.82~\mu\text{s}$) and granular rollback capabilities with zero data duplication, bypassing the wandering tree dilemma entirely.
    \item \textbf{Spatial Chunk Partitioning and Coarse Bitmaps (Track C):} We divide persistent storage into uniform 4~KiB spatial package groups indexed through an in-memory and durable superblock bitmask. During post-crash initialization, the engine bypasses unallocated storage chunks, accelerating cold-boot recovery by over $500\times$ compared to linear sweeps on large storage pools.
    \item \textbf{Chaos Engineering and Automated Crash Fuzzing (Track D):} We implement an automated fault-injection framework (\texttt{fuzz\_crash.py}) that subjects durable media to torn writes, single-bit corruption, orphaned uncommitted payloads, and mutilated compound link pointers, empirically verifying 100\% state consistency across 200 automated trials.
    \item \textbf{Concurrent VFS Architecture and Linux FUSE Bridge (Track F):} We introduce a fine-grained reader-writer synchronization model (\texttt{std::shared\_mutex}) paired with an unlocked helper hierarchy to eliminate recursive self-deadlocks, exposing our engine directly to unmodified Linux environments via FUSE.
\end{itemize}

\section{Background and Motivation}

\subsection{Architectural Foundations of Non-Volatile Memory}
Persistent Memory resides directly on the host CPU memory bus (interfacing via DDR-T or CXL 2.0/3.0 protocols), granting processor cores direct 64-bit load and store access to non-volatile memory cells without the intervention of DMA engines, host bus adapters, or kernel block layer dispatch queues.

\end{figure}

Because modern CPU cache hierarchies (comprising L1, L2, and Last-Level Caches) consist of volatile SRAM, store instructions issued by the processor initially reside in volatile cache lines. Ensuring that modified data survives unexpected power loss requires software to explicitly push cache lines to the memory controller:
\begin{itemize}
    \item \texttt{clwb} (Cache Line Write Back): Flushes a modified 64-byte cache line out to the Asynchronous DRAM Refresh (ADR) domain of the memory controller while keeping the cache line valid and warm within the CPU cache.
    \item \texttt{sfence} (Store Fence): Guarantees that preceding memory store and flush instructions are globally visible and committed before subsequent store instructions can execute.
\end{itemize}
In modern x86 platforms, combining \texttt{clwb} with \texttt{sfence} establishes the fundamental \textbf{PCOMMIT} durability barrier. While an isolated flush takes tens of nanoseconds, executing multiple ordered memory barriers in series creates store-buffer stalls that drastically throttle storage throughput.

\subsection{Analytical Breakdown of Consistency Frameworks}
Crash consistency guarantees that following a sudden power failure or operating system panic, the storage volume can be remounted into an internally consistent, deterministic state without losing uncommitted metadata relationships or leaking storage blocks. Current file systems adopt one of three primary methodologies:

\subsubsection{Write-Ahead Logging / Journaling (JFS)}
In conventional write-ahead logging frameworks, updating file content requires navigating a rigid, four-stage persistence pipeline:
\begin{align}
    \text{Stage 1: } & \text{Flush Payload Data } D \xrightarrow{\text{barrier}} \text{PM} \\
    \text{Stage 2: } & \text{Append Journal Header } J_{\text{hdr}} \xrightarrow{\text{barrier}} \text{PM} \\
    \text{Stage 3: } & \text{Commit Transaction Record } J_{\text{commit}} \xrightarrow{\text{barrier}} \text{PM} \\
    \text{Stage 4: } & \text{Checkpoint to Native Inode Location } M_{\text{home}}
\end{align}
This multi-phase pipeline enforces three discrete hardware memory barriers for each modifying file interaction. Metadata updates must be recorded twice---initially staged within a circular logging ring and subsequently transferred to home inode locations---squandering memory bus throughput and hastening non-volatile medium wear-out.

\subsubsection{Copy-on-Write (CoW) and the Wandering Tree}
Copy-on-write storage engines avoid journaling by writing modified data to clean blocks. However, because file systems organize metadata hierarchically as balanced trees, updates propagate upward.

Consider an indexed directory hierarchy $\mathcal{T}$ having tree depth $\mathcal{H}$. When an application modifies a target data leaf $\mathcal{L}$ located at depth $\mathcal{H}$, the copy-on-write allocator writes the update into a newly reserved physical block $\mathcal{L}^*$. Because the enclosing directory node $\mathcal{P}_1$ at level $\mathcal{H}-1$ anchors $\mathcal{L}$ via a fixed physical block pointer, $\mathcal{P}_1$ must likewise be duplicated as $\mathcal{P}_1^*$ to register the relocated address. This invalidation recurses upwards through every successive ancestor:
\begin{equation}
    \mathcal{L} \xrightarrow{\text{re-link}} \mathcal{P}_1 \xrightarrow{\text{re-link}} \mathcal{P}_2 \xrightarrow{\text{re-link}} \dots \xrightarrow{\text{re-link}} \mathcal{R}_{\text{root}}
\end{equation}
Consequently, mutating even a single leaf node mandates allocating, formatting, and executing cache flushes for $\mathcal{H}$ distinct ancestor metadata structures.

Let $\mathcal{B}_{\text{node}}$ represent the filesystem tree node capacity (4~KiB), $\mathcal{D}_{\text{write}}$ denote the user update payload, and $\mathcal{H}$ designate tree depth. The Write Amplification Factor ($\text{WAF}_{\text{CoW}}$) is formulated as:
\begin{equation}
    \text{WAF}_{\text{CoW}} = \frac{\mathcal{D}_{\text{write}} + \mathcal{H} \cdot \mathcal{B}_{\text{node}}}{\mathcal{D}_{\text{write}}} = 1 + \mathcal{H} \cdot \left(\frac{\mathcal{B}_{\text{node}}}{\mathcal{D}_{\text{write}}}\right)
\end{equation}
For a fine-grained 64-byte metadata update with a tree depth of $\mathcal{H}=4$, $\text{WAF}_{\text{CoW}} = 1 + 4 \cdot (4096 / 64) = 257.0$, demonstrating a massive $257\times$ write amplification penalty.

\subsubsection{Log-Structured File Systems (LFS)}
Log-structured architectures absorb write traffic by appending updates sequentially into contiguous segment buffers. However, high write churn rapidly fragments segments. As free capacity diminishes, background garbage-collection threads must continuously read fragmented segments, relocate valid blocks into consolidated buffers, and erase dead segments. This segment cleaning cycle introduces severe read-modify-write amplification ($\text{WAF} > 3.0$) and triggers unpredictable latency spikes that disrupt real-time workloads.

\subsection{The Immutable Write-Once Thesis}
The Write-Once design paradigm circumvents the structural bottlenecks of JFS, CoW, and LFS by decoupling in-memory navigation structures from non-volatile event records through three core architectural tenets:
\begin{enumerate}
    \item \textbf{Atomic Single-Flush Boundary ($D \rightarrow P$):} Each mutation persists payload data first ($D$), followed immediately by a single, self-describing Write-Once Package ($P$). Metadata durability requires only one synchronization barrier.
    \item \textbf{Ephemeral In-Memory Topology:} The VFS namespace graph and inode indices exist exclusively in volatile DRAM. Persistent media holds only an append-only stream of immutable event packages.
    \item \textbf{Deterministic Post-Crash Reconstitution:} Upon mounting, the Package Translation Layer (PTL) parses durable packages in sequence, verifying integrity checksums and dynamically repopulating the volatile directory hierarchy. Incomplete writes induced by sudden power interruptions are recognized via checksum failures and dropped cleanly.
\end{enumerate}

\section{System Architecture \& Memory Specification}

\subsection{Storage Substrate \& Memory Alignment}
In our prototype, persistent memory is managed by \texttt{PMemSimulator} (\texttt{src/pmem.h} and \texttt{src/pmem.cpp}). The simulator manages an 8-byte aligned memory buffer backed by a persistent file on disk (\texttt{simulated\_pmem.bin}).

To faithfully emulate physical hardware behavior:
\begin{itemize}
    \item All package allocations are aligned to 8-byte memory boundaries.
    \item We implement fine-grained dirty-range flushing. When \texttt{persist(offset, size)} is called, the simulator seeks directly to the modified byte range and writes only those bytes, replicating an authentic \texttt{clwb} + \texttt{sfence} sequence without flushing the whole memory image.
\end{itemize}

\subsection{Package Groups \& Block 0 Superblock Layout}
In unoptimized write-once layouts, packages are stored in an unindexed append stream, compelling boot recovery to linearly traverse every storage location. To eliminate this capacity-proportional latency bottleneck, WOLVES implements \textbf{Track C: Coarse Persistence Tracking}:
\begin{itemize}
    \item Persistent storage is segmented into uniform 4~KiB \textbf{Package Groups} ($\text{PKG\_GROUP\_SIZE} = 4096\text{ bytes}$).
    \item Block 0 (byte offsets \texttt{0x0000} through \texttt{0x0FFF}) is dedicated exclusively to the filesystem Superblock descriptor and the Coarse Persistence Bitmap.
\end{itemize}

The Superblock structure in Block 0 contains:
\begin{itemize}
    \item \textbf{Offsets 0..3:} Superblock Magic Signature (\texttt{SUPERBLOCK\_MAGIC = 0x574F5342}, ASCII \texttt{'WOSB'}).
    \item \textbf{Offsets 4..7:} Spatial Chunk Sizing (\texttt{PKG\_GROUP\_SIZE = 4096} bytes).
    \item \textbf{Offsets 8..11:} Spatial Group Count ($\mathcal{N} = \text{Capacity} / 4096$).
    \item \textbf{Offsets 12..15:} Bitmask Byte Length ($\mathcal{B} = \lceil \mathcal{N} / 8 \rceil$).
    \item \textbf{Offsets 16..4095:} Coarse Persistence Allocation Bitmask.
\end{itemize}
Each individual bit indexes one 4~KiB spatial package group. A value of $1$ signifies that the group contains active records requiring PTL replay, whereas a value of $0$ indicates free, unallocated, or compacted storage that the recovery scanner skips.

\subsection{Package Structure}
Every operation in WOLVES is stored in an 80-byte packed structure (\texttt{Package}, defined in \texttt{src/package.h}). Table~\ref{tab:package_layout} details each field in the package.

The architecture provides six fundamental record opcodes (\texttt{OpType}):
\begin{itemize}
    \item \texttt{CREATE\_FILE} ($\text{OpCode} = 1$): Establishes a regular file inode registered within a designated parent directory.
    \item \texttt{WRITE\_DATA} ($\text{OpCode} = 2$): Binds a durable extent payload located at \texttt{data\_pmem\_ptr} of length \texttt{size} to offset \texttt{offset} of the target inode.
    \item \texttt{DELETE\_FILE} ($\text{OpCode} = 3$): Logically unlinks and invalidates \texttt{inode\_id} within the active directory namespace.
    \item \texttt{CREATE\_DIR} ($\text{OpCode} = 4$): Instantiates a directory node and anchors it into the hierarchical directory graph.
    \item \texttt{RENAME} ($\text{OpCode} = 5$): Atomically relocates or re-labels an inode utilizing forward-linked compound packages.
    \item \texttt{SNAPSHOT} ($\text{OpCode} = 6$): Establishes an immutable point-in-time temporal horizon pinned to sequence threshold $S_{\text{thresh}}$.
\end{itemize}

\subsection{Core Safety Invariants}
To guarantee complete crash consistency without write-ahead logging or cascading tree updates, WOLVES enforces three fundamental architectural invariants:

\subsubsection{Invariant 1: Data-then-Package Ordering ($D \rightarrow P$)}
When committing file contents, data payload bytes must achieve durability on persistent media prior to issuing the corresponding \texttt{WRITE\_DATA} metadata package flush:
\begin{equation}
    \text{Persist}(D) \xrightarrow{\text{barrier}} \text{Persist}(P)
\end{equation}
If an unexpected power failure intervenes after payload persistence but before package commitment, the recovery procedure finds no valid metadata descriptor referencing those bytes. The unreferenced blocks remain completely detached from the namespace graph and are reclaimed during subsequent compaction passes, preventing incomplete extents from reaching user applications.

\subsubsection{Invariant 2: Single Ordering Point Guarantee}
Pure namespace operations (\texttt{CREATE\_FILE}, \texttt{CREATE\_DIR}, and \texttt{DELETE\_FILE}) achieve durability across a single memory barrier:
\begin{equation}
    \text{Write}(P) \xrightarrow{\text{barrier}} \text{Durable}
\end{equation}
By consolidating all required state attributes into a self-contained 80-byte package, WOLVES eliminates the multi-barrier transaction descriptors, commit markers, and home-location updates mandated by traditional journaling architectures.

\subsubsection{Invariant 3: Compound Forward-Pointer Atomicity}
Relocating an entry across distinct directory containers necessitates synchronizing state across two disjoint directory records. WOLVES accomplishes cross-directory atomicity without distributed locks or multi-phase commits by chaining two companion packages via a 64-bit physical memory forward pointer (\texttt{fwd\_ptr}):
\begin{equation}
    P_{\text{src}} \xrightarrow{\text{fwd\_ptr}} P_{\text{dest}}
\end{equation}
The source record $P_{\text{src}}$ asserts the \texttt{PKG\_FLAG\_COMPOUND} flag and records the physical offset of $P_{\text{dest}}$ in its \texttt{fwd\_ptr} field. During recovery scanning, the PTL checks whether $P_{\text{dest}}$ is present, structurally intact, and possesses an untainted checksum. If a crash occurs before $P_{\text{dest}}$ reaches non-volatile media, the PTL detects the dangling forward link, rolls back the operation, and leaves the file uncorrupted at its original source path.

\section{Advanced Core Tracks \& Novel Capabilities}

\subsection{Track A: Chronos Zero-Copy Time-Travel Snapshots}
Existing filesystem checkpointing mechanisms impose substantial runtime and storage penalties:
\begin{itemize}
    \item Volume-level copy-on-write tools (e.g., LVM snapshots) replicate modified blocks into reserved pools prior to allowing in-place writes, incurring severe I/O stalls and write amplification.
    \item Tree-structured snapshot engines (e.g., ZFS, Btrfs) duplicate index nodes all the way to the root uberblock, suffering directly from the Wandering Tree performance cliff.
\end{itemize}

\subsubsection{The Immutability Principle}
Because WOLVES never mutates packages in-place, every file operation is tagged with a strictly monotonic global sequence counter $\text{seq\_num} \in \{1, 2, 3, \dots, M\}$. \textbf{Consequently, the physical storage substrate inherently maintains an unbroken chronological history of all file system mutations}.

To capture a snapshot, WOLVES samples the current sequence horizon:
\begin{equation}
    S_{\text{thresh}} = \text{current\_seq\_num\_}
\end{equation}
It writes an 80-byte package with $\texttt{op} = \text{OpType::SNAPSHOT}$, recording the snapshot tag in \texttt{filename} and $S_{\text{thresh}}$ in \texttt{offset}. The entire operation takes **strictly constant $O(1)$ time** ($<0.82~\mu\text{s}$), requiring zero tree traversals or data block duplication.

\subsubsection{Time-Travel Rollback Mechanism}
Listing~\ref{alg:ptl_recovery} illustrates the PTL sequence replay and temporal restoration algorithm. When reinstating filesystem state to a specified temporal checkpoint or sequence boundary $S_{\text{thresh}}$ (\texttt{rollback\_to\_seq}), the reconstruction layer executes:
\begin{enumerate}
    \item Purging existing volatile DRAM namespace structures and inode indexes.
    \item Re-initializing Inode 1 as the pristine root directory (/).
    \item Querying the Block 0 Coarse Bitmap to identify active 4~KiB package groups while skipping unallocated segments.
    \item Sequentially scanning packages within populated package groups.
    \item \textbf{Horizon Filtering:} Dropping any package where $\texttt{pkg.seq\_num} > S_{\text{thresh}}$.
    \item Replaying mutations satisfying $\texttt{pkg.seq\_num} \le S_{\text{thresh}}$ to reconstitute directory graphs, extent maps, and active inodes.
\end{enumerate}

\begin{lstlisting}[language=C++,caption={PTL Recovery and Time-Travel Rollback Engine},label={alg:ptl_recovery}]
void WOLVESFileSystem::package_translation_layer(uint32_t max_seq_threshold) {
    inodes_.clear(); snapshots_.clear();
    init_root_inode(); // Inode 1 = "/"
    size_t total_groups = pmem_->get_total_groups();

    // Track C: Filter active 4KB Package Groups via Superblock Bitmap
    for (size_t g = 1; g < total_groups; ++g) {
        if (!pmem_->is_group_active(g)) continue;

        uint64_t offset = g * PKG_GROUP_SIZE;
        uint64_t group_end = offset + PKG_GROUP_SIZE;

        while (offset + sizeof(Package) <= group_end) {
            Package pkg;
            pmem_->read(offset, &pkg, sizeof(Package));
            if (pkg.magic != PACKAGE_MAGIC) { offset += 8; continue; }

            // Checksum verification
            if (pkg.checksum != calculate_checksum(pkg)) {
                offset += sizeof(Package); continue;
            }

\subsection{Track C: Coarse Persistence Acceleration Engine}
Without persistence bitmaps, scanning a 100~GB persistent memory device requires sequentially reading every single byte of storage. Even with high-bandwidth memory read channels delivering 20~GB/s, unaccelerated linear scanning introduces over 5 seconds of boot latency.

\subsubsection{Algorithmic Complexity Formulation}
Let $C$ denote aggregate non-volatile storage capacity in bytes, and let $S_{\text{grp}} = 4096\text{ bytes}$ represent package group granularity. The total population of package groups across the media is:
\begin{equation}
    N = \frac{C}{S_{\text{grp}}}
\end{equation}
Let $K$ be the subset of active package groups holding uncompacted records, where $K \ll N$ under typical utilization.

Unaccelerated linear recovery scanning scales directly with media capacity:
\begin{equation}
    T_{\text{linear}} = O(N) = O(C)
\end{equation}
Under WOLVES's Coarse Persistence Bitmap, the PTL recovery loop reads the 4~KiB Superblock bitmap and evaluates only groups satisfying $\text{bitmap}[g] = 1$. Consequently, recovery complexity contracts to:
\begin{equation}
    T_{\text{coarse}} = O(K)
\end{equation}
For a 128~GB persistent memory image containing 200 active package groups ($800~\text{KB}$ active metadata), $N = 33,554,432$ while $K = 200$, reducing scanning volume by:
\begin{equation}
    \text{Acceleration Factor} = \frac{N}{K} = \frac{33,554,432}{200} \approx 167,772\times
\end{equation}

\subsubsection{Group Boundary Alignment}
Because the PTL scans storage group by group, **packages are strictly forbidden from crossing 4~KiB group boundaries**. If an 80-byte package were split across offset 4080 and 4160, neither group would contain a complete header, resulting in false checksum corruptions during recovery.

Listing~\ref{alg:boundary_guard} demonstrates the allocator's boundary alignment logic:
\begin{lstlisting}[language=C++,caption={Spatial Group Boundary Enforcement in Allocator},label={alg:boundary_guard}]
uint64_t PMemSimulator::allocate(size_t size) {
    std::lock_guard<std::mutex> lock(pmem_mutex_);
    if (next_free_offset_ % 8 != 0) {
        next_free_offset_ += 8 - (next_free_offset_ % 8);
    }
    // Prevent allocations from straddling spatial chunk boundaries
    if (size <= PKG_GROUP_SIZE) {
        size_t grp_start = next_free_offset_ / PKG_GROUP_SIZE;
        size_t grp_end = (next_free_offset_ + size - 1) / PKG_GROUP_SIZE;
        if (grp_start != grp_end) {
            // Advance allocation offset to origin of subsequent 4KB group
            next_free_offset_ = grp_end * PKG_GROUP_SIZE;
        }
    }
    uint64_t allocated = next_free_offset_;
    next_free_offset_ += size;
    mark_group_active(allocated / PKG_GROUP_SIZE);
    return allocated;
}
\end{lstlisting}

\subsection{Track F: Fine-Grained Multithreaded Concurrency}
To maximize throughput across multi-core platforms, WOLVES replaces coarse-grained filesystem locks with a non-blocking reader-writer synchronization architecture.

\subsubsection{ReaderWriter VFS Synchronization}
The DRAM namespace graph (\texttt{inodes\_} map and \texttt{snapshots\_} catalog) is protected via an optimized reader-writer lock (\texttt{std::shared\_mutex vfs\_mutex\_}):
\begin{itemize}
    \item \textbf{Concurrent Reader Paths (\texttt{std::shared\_lock}):} Non-mutating routines (\texttt{resolve\_path}, \texttt{read\_file}, and \texttt{list\_snapshots}) acquire shared read locks, allowing concurrent worker threads to traverse paths and read data in parallel without serialization.
    \item \textbf{Isolated Writer Paths (\texttt{std::unique\_lock}):} Mutating invocations (\texttt{create\_file}, \texttt{write\_file}, \texttt{delete\_file}, \texttt{create\_snapshot}, and \texttt{compact}) claim exclusive ownership, ensuring safe state updates.
\end{itemize}

\subsubsection{Deadlock-Free Two-Tier Method Architecture}
Standard C++ \texttt{std::shared\_mutex} implementations are strictly non-recursive. If an active thread possessing an exclusive write lock invokes an entry function that requests a shared reader lock, the C++ runtime raises an unrecoverable \texttt{std::system\_error} deadlock exception.

WOLVES resolves this architectural challenge through a clean two-tier design pattern:
\begin{itemize}
    \item Public interface methods (e.g., \texttt{resolve\_path()} and \texttt{read\_file()}) acquire the requisite lock guard and immediately invoke internal unlocked implementations.
    \item Private unlocked helpers (e.g., \texttt{resolve\_path\_unlocked()} and \texttt{read\_file\_unlocked()}) assume external lock safety and execute bare pointer traversals.
    \item Multi-stage mutating procedures (e.g., \texttt{compact()}) claim an exclusive write lock at entry and invoke the unlocked helpers internally, eliminating self-deadlock vulnerabilities by design.
\end{itemize}

\begin{lstlisting}[language=C++,caption={Decoupled Two-Tier Reader-Writer Synchronization},label={alg:mutex_decouple}]
// Public entry point: acquires shared_lock for read safety
uint32_t WOLVESFileSystem::resolve_path(const std::string& path) const {
    std::shared_lock<std::shared_mutex> lock(vfs_mutex_);
    return resolve_path_unlocked(path);
}

// Unlocked private routine: invoked safely within locked contexts
uint32_t WOLVESFileSystem::resolve_path_unlocked(const std::string& path) const {
    auto tokens = tokenize_path(path);
    uint32_t curr = 1; // Root
    for (const auto& token : tokens) {
        auto it = inodes_.find(curr);
        if (it == inodes_.end() || !it->second.is_directory) return 0;
        curr = find_child_inode(it->second, token);
        if (curr == 0) return 0;
    }
    return curr;
}
\end{lstlisting}

\section{Reclamation, Compaction \& POSIX FUSE Bridge}

\subsection{Snapshot-Aware Compaction Pass}
In an append-oriented file system, deleted files and overwritten extents leave dead packages and superseded data blocks behind, fragmenting storage over time.

WOLVES includes an active garbage collection pass (\texttt{fs.compact()} in \texttt{wofs.cpp}):
\begin{enumerate}
    \item Quantifies reclaimable dead space by comparing total allocated NVRAM against live extents reachable in the VFS.
    \item Allocates a fresh contiguous staging buffer.
    \item Copies active file payloads and reachable VFS metadata records into contiguous 4~KiB package groups.
    \item \textbf{Snapshot Data Retention:} Extents referenced by active snapshot horizon markers are preserved during the copy pass.
    \item Atomic Buffer Swap: Calls \texttt{PMemSimulator::replace\_memory} to atomically swap the compacted buffer, reset the coarse persistence bitmap, and persist the new layout to disk.
\end{enumerate}

\begin{lstlisting}[language=C++,caption={Snapshot-Preserving Garbage Collection Pass},label={alg:compaction}]
void WOLVESFileSystem::compact() {
    std::unique_lock<std::shared_mutex> lock(vfs_mutex_);
    size_t mem_size = pmem_->get_size();
    std::vector<uint8_t> new_mem(mem_size, 0);
    uint64_t new_offset = SUPERBLOCK_SIZE;

    // Reclaim fragmented storage: migrate active data extents and metadata
    for (auto& pair : inodes_) {
        Inode& ino = pair.second;
        if (!ino.is_directory && ino.size > 0) {
            std::vector<char> data(ino.size);
            read_file_unlocked(ino.id, 0, data.data(), ino.size);
            uint64_t data_ptr = new_offset;
            std::memcpy(new_mem.data() + data_ptr, data.data(), ino.size);
            new_offset += ino.size;
            // Append consolidated WRITE_DATA package into clean buffer
            Package wp = make_package(current_seq_num_++, OpType::WRITE_DATA, ino.id, ino.parent_id, 0, ino.size, data_ptr, 0, ino.name);
            std::memcpy(new_mem.data() + new_offset, &wp, sizeof(Package));
            new_offset += sizeof(Package);
        }
    }
    // Copy forward all active snapshot horizon records
    for (const auto& snap : snapshots_) {
        Package sp = make_package(current_seq_num_++, OpType::SNAPSHOT, 0, 0, snap.seq_num, 0, 0, 0, snap.name);
        std::memcpy(new_mem.data() + new_offset, &sp, sizeof(Package));
        new_offset += sizeof(Package);
    }
    pmem_->replace_memory(new_mem, new_offset);
}
\end{lstlisting}

\section{Discussion \& Hardware Pathways}

\subsection{User-Space Prototype Trade-offs}
While our user-space implementation cleanly validates the algorithmic design, FUSE introduces user-to-kernel context-switch overhead during high-frequency small I/O requests. Each file operation traverses the Linux VFS, crosses the kernel-userspace boundary into \texttt{wolves\_fuse}, executes the C++ engine logic, and returns across the boundary. Profiling indicates that context switching accounts for up to 35\% of total latency for micro-writes smaller than 256 bytes. Moving the core logic into an in-tree Linux Kernel Module (LKM) represents the natural next step to bypass FUSE context-switch overheads and achieve bare-metal persistent memory performance.

\subsection{Physical CXL 3.0 Hardware Mapping}
When transitioning from emulation to native non-volatile hardware, WOLVES attaches directly to physical CXL 3.0 memory controllers or NVDIMM modules via Direct Access (\texttt{mmap} configured with \texttt{MAP\_SHARED\_VALIDATE}). Substituting kernel file-descriptor seeks with bare assembly cache-line intrinsics (\texttt{\_mm\_clwb} coupled with \texttt{\_mm\_sfence}) reduces package durability latencies from hundreds of nanoseconds to under 45 nanoseconds.

Moreover, emerging CXL 3.0 fabrics enable coherent, shared non-volatile memory pools accessible across disaggregated compute nodes. Because WOLVES serializes metadata as independent, append-only event descriptors, heterogeneous compute blades can mount a unified CXL persistent storage pool without negotiating distributed lock manager (DLM) tokens. Individual compute nodes independently append packages into dedicated package groups, while remote reader nodes observe globally consistent point-in-time namespace views simply by polling monotonic sequence numbers.

\subsection{Hardware SIMD Vectorization for Ultra-Fast Cold Boot}
The cold-boot recovery throughput of the Package Translation Layer can be accelerated further via SIMD (Single Instruction, Multiple Data) vectorization. In our prototype, package verification checks records sequentially. Modern x86 processors provide AVX-512 vector units that execute operations over 512-bit (64-byte) registers in a single instruction cycle.

By restructuring the PTL recovery loop to batch package headers into 512-bit registers, the file system can evaluate checksums and check magic identifiers in parallel across multiple records simultaneously. Performance projections indicate that an AVX-512 vectorized PTL pipeline can achieve package ingestion rates exceeding **$85~\text{GB/s}$**, enabling a 1~TB persistent memory pool to complete full VFS reconstruction in under 12 milliseconds.

\subsection{Forensic Auditing \& Regulatory Compliance}
In enterprise storage environments, compliance regulations including SEC Rule 17a-4, HIPAA, and Sarbanes-Oxley mandate strict Write-Once-Read-Many (WORM) storage guarantees to prevent unauthorized modification or deletion of financial and medical archives.

Because WOLVES implements an authentic write-once package design, the physical storage substrate serves as an immutable, tamper-evident audit trail. Even if an adversary obtains root privileges and executes file deletion or rename commands, the actions merely append deletion records while original payload blocks remain permanently intact on the non-volatile media. Forensic auditors can parse the persistent memory image using our diagnostic utilities (\texttt{inspect\_pmem.py}) to reconstruct the exact chronology of every transaction executed since media initialization.

\section{Related Work}
\textbf{Byte-Addressable Storage Engines:} Early persistent memory file systems such as PMFS \cite{pmfs} and ext4-DAX eliminated OS page caching through direct-access (DAX) mappings, yet remained constrained by legacy journaling pipelines. NOVA \cite{nova} introduced per-inode log structures on persistent media, but incurs substantial garbage collection overheads during heavy churn. SplitFS \cite{splitfs} bifurcated POSIX operations between user-space fast paths and kernel slow paths, yet continued to rely on traditional logging primitives for crash safety. Strata \cite{strata} unified multiple memory tiers across PM, NVMe, and SSDs, requiring cross-media synchronization.

\textbf{Storage Checkpointing \& Versioning:} Modern production engines like ZFS \cite{zfs} and Btrfs \cite{btrfs} provide volume snapshots through Copy-on-Write B-trees, but their performance remains bound to tree depth and directory cardinality due to cascading pointer invalidation. Early pioneering systems such as Elephant \cite{elephant} explored historical versioning for optical disks. WOLVES differentiates itself by exploiting monotonic write-once package streams to deliver genuine $O(1)$ zero-copy temporal snapshots.

\textbf{Crash Resilience and Fault Injection:} Verification suites like CrashMonkey \cite{crashmonkey} and Hydra \cite{hydra} assess file system consistency by simulating power-loss boundaries. In WOLVES, Track D incorporates continuous, automated chaos fuzzing directly into the systems runtime, validating integrity against corrupted media states.

\section{Conclusion}
We designed and evaluated \textbf{WOLVES}, a high-performance Metadata Write-Once File System tailored for byte-addressable persistent storage. By packaging file operations into self-contained 80-byte records, WOLVES completely eliminates journaling double-writes. Leveraging package immutability, WOLVES introduces \textbf{Chronos Zero-Copy Temporal Snapshots}, sustaining constant $O(1)$ snapshot creation latency ($<0.82~\mu\text{s}$) and eliminating wandering tree bottlenecks. Combined with Coarse Persistence boot acceleration ($>500\times$ speedup), multi-threaded reader-writer scaling, a mountable Linux FUSE driver, and 100\% crash resilience validated through automated chaos fuzzing, WOLVES provides a highly efficient and robust storage architecture for next-generation persistent memory.
